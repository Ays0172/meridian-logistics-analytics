# Day 5 — Solutions

## Spaced recall

1. Parquet embeds its own schema in every file and matches columns by name, not position, so a reordered partition still aligns correctly; CSV has no embedded schema, only positional values, so a reordered CSV file would silently shift every value into the wrong column.
2. `try … otherwise` catches genuine type-conversion failures (a cell that could not become the target type at all, surfaced as an `[Error]` value) — it must never be used as a proxy for "this value looks unusual" or "this value is negative," because a correctly-converted negative number is not an error by any definition Power Query uses.
3. For any day-of-month 12 or below, the conversion succeeds silently with day and month swapped, producing a wrong-but-plausible date with no error raised at all — the exact opposite of a loud failure you'd notice.
4. Because query folding, in the sense "View Native Query" checks for, is a relational/OData concept — flat-file and folder-based connectors (CSV, Parquet, the Folder connector) have no native query language to translate M into, so the option is simply unavailable, not broken.
5. Recover `Year`/`Month` from `[Folder Path]` **before** invoking the per-file combine function — if you derive the partition value from something inside the file instead, or after combining, you lose the guarantee that the value reflects the actual folder the row came from.
6. Any two of: nulls in optional fields (leave null, don't zero-fill), duplicated `BookingNo` (dedupe on latest `BookingDateKey`, document the rule), mixed casing/whitespace in `LocationName` (`Text.Trim` + `Text.Proper`), two spellings of the same country (a mapping table, not find-and-replace), late-arriving dimension references (route to `-1`, report the count), implausible `NominalTeuCapacity` outliers (flag, don't drop), leading-zero `SkuCode` (import as text explicitly).

## Drill 1 — Cardinality classification

(a) **`DimCarrier` → `FactContainerMove`: one-to-many.** One carrier operates many equipment-move events; `FactContainerMove.CarrierKey` is the many-side FK.

(b) **`DimEquipment` → `FactShipment`: one-to-many.** One equipment type/size (e.g. `40HC`) is used by many shipments; `FactShipment.EquipmentKey` is the many-side FK.

(c) **`FactBooking` → `FactShipment` (via `BookingKey`): one-to-many, though close to one-to-zero-or-one in practice.** Per Day 1's entity chain, a booking normally produces at most one shipment (only occasionally splitting into more than one house bill), so while the *contract's* cardinality label is one-to-many like every other fact-to-fact link here, the realistic distribution is heavily skewed toward exactly one shipment per booking — worth stating both the formal cardinality and the practical distribution, since a purist "one-to-many" label alone slightly overstates how often a booking really does fan out.

(d) **One-to-one**, and the follow-up: **seriously consider not creating `DimVesselCrewRoster` as a separate table at all — fold its columns directly into `DimVessel` instead.** A 1:1 relationship between two dimension tables is the textbook design smell from §1: if every vessel has exactly one crew-roster row and every crew-roster row belongs to exactly one vessel, splitting them buys nothing (no compression benefit, per Day 3's VertiPaq reasoning) and costs a relationship hop on every query that needs both a vessel attribute and a crewing attribute together. The only legitimate reason to keep them separate would be if crew-roster data changes on a completely different cadence or ownership boundary than the rest of `DimVessel` (e.g., a different system of record, a different SCD pattern) — worth naming as the one case where 1:1 is defensible, but absent that reason, merge them.

## Drill 2 — Location role-play

A correct build has four distinct tables in the model — `DimLocationOrigin`, `DimLocationDestination`, `DimLocationPol`, `DimLocationPod` — each a full copy of `DimLocation`'s structure, each with exactly one relationship: `DimLocationOrigin[LocationKey] → FactShipment[LocationKeyOrigin]`, and so on for the other three. With a `CountryName` slicer built from `DimLocationOrigin` and a second from `DimLocationDestination` on the same page, both should independently narrow a shipment-count visual, and combining both (e.g., origin = India, destination = Netherlands) should narrow it further, consistent with an AND across two independent filters. If instead you tried to solve this with one shared `DimLocation` table and `USERELATIONSHIP`, you'd find you can get *one* role active in a measure but cannot get two independent slicers to each visibly filter by a different role at the same time — which is exactly the limitation §5 describes, and precisely why this drill asks you to build the multiple-import version rather than attempt the single-table version first.

## Drill 3 — Date role-play and USERELATIONSHIP

With `ShipmentDateKey` active and the other three inactive, `COUNTROWS(FactShipment)` sliced by a `DimDate` year filter counts shipments whose **departure** fell in that year. `Shipments by ETA` (using `USERELATIONSHIP(FactShipment[EtaDateKey], DimDate[DateKey])`) counts shipments whose **ETA** fell in that year instead. These two measures will differ for any year where shipments departing in, say, late December have an ETA falling in January of the following year (or the reverse near any year boundary, and more generally wherever `ActualTransitDays` pushes an ETA across a month or year line relative to departure) — the exact size of the discrepancy depends on your specific data, but the direction of the explanation is what's being marked: the two measures are deliberately asking "how many shipments *departed* in year X" versus "how many shipments have an ETA *in* year X," and those are different populations whenever transit time crosses a year boundary.

## Drill 4 — Breaking it on purpose

With the `ShipmentDateKey` relationship set to inactive, the card visual showing `SUM(FactShipment[Revenue_usd])` **does not change at all** when the year slicer is changed — it continues to display the grand total across every year, exactly as if no slicer existed on the page. This is the precise symptom to internalise: not an error message, not a blank visual, not an obviously wrong number — a number that looks completely plausible and simply **stops responding** to a filter that visibly exists and visibly has a selection made in it. Restoring the relationship to active immediately restores normal slicer behaviour, with no other change needed. If your observation was instead "the visual went blank" or "it showed an error," re-check that you actually deactivated the relationship (rather than, say, deleting it) — a deleted relationship behaves differently (Power BI will often flag the visual with a "can't determine relationship" style warning) from an inactive one, which is deliberately silent.

## Drill 5 — The ambiguity argument

A strong answer: "`FactBooking` and `FactShipment` are already directly related via `BookingKey`, and `DimCustomer` already relates directly to both of them via `CustomerKey`. Making `DimCustomer`–`FactBooking` bidirectional opens a second route by which a filter on `FactShipment` could reach `DimCustomer` — once directly, and once by flowing backward through `FactBooking` — which is exactly the ambiguous-cycle shape Power BI's engine is designed to prevent, either by refusing to create the relationship as specified or by producing behaviour that depends on internal evaluation order rather than a clear, single filter path. The safer alternative, if the actual need is 'let a customer-list visual respond to shipment-level filters,' is to build that specific behaviour as an explicit measure — for instance, a `DimCustomer`-side measure using `CALCULATE` with a filter expressed via `TREATAS` or an explicit table-filter argument that reaches into `FactShipment` only for that one calculation — rather than a standing bidirectional relationship that changes filter behaviour for every visual on every page, including ones that never needed it."

Partial credit for correctly naming the triangle and rejecting the bidirectional toggle, even without naming a specific DAX alternative — the core of the answer is recognising *why* the risk exists (the pre-existing fact-to-fact relationship), not memorising one specific fix.
