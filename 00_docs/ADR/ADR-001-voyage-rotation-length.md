# ADR-001 — Lengthen DimVoyage rotations to realistic loop sizes

**Status:** Accepted
**Date:** 2026-08-21
**Affects:** `DimVoyage.RotationString`, `DimVoyage.PortCallCount`, `FactPortCall`

## Context

`DimVoyage` as first built carried rotations of 4–6 port calls, and
`PortCallCount` agreed with the rotation string, so the dimension was internally
consistent. It was still wrong.

`FactPortCall` is generated by exploding each voyage's rotation, one row per port
called. With 6,799 voyages at 4.59 calls each, the maximum achievable row count
was 31,175 against a contracted 96,000 — a 67% shortfall that no amount of
sampling could close, because the rows simply did not exist to be sampled.

The row count was the symptom. The real problem was that a 4–6 port rotation is
not what a deep-sea liner service looks like. An Asia–North Europe string
typically calls at three or four Chinese load ports, a South-East Asian hub,
sometimes a Mediterranean or Suez-adjacent call, then four or five North
European discharge ports — 12 to 16 calls in one direction. Under-length
rotations degraded three things at once:

- **Berth productivity and dwell** had too few observations per voyage to show
  the variation those KPIs exist to expose.
- **Transhipment analysis** was near-meaningless with at most one intermediate
  hub per rotation.
- **The congestion set-piece** (contract §3.3) could only reach a small number of
  port calls at the affected ports, weakening the signal the Week 3 exercise asks
  the learner to find.

## Decision

Rewrite `RotationString` and `PortCallCount` in place via
`01_generator/revise_voyage_rotations.py`, composing each rotation as:

    4–8 load ports (origin trade region)
  + 2–4 corridor hubs (chosen from a per-corridor list of real transhipment hubs)
  + 4–8 discharge ports (destination trade region)

with immediately-repeated ports collapsed, and the direction reversed for
backhaul voyages. Every port code is drawn from `DimLocation`, so no rotation can
reference a port that does not exist.

Result: mean 15.0 calls per voyage (min 10, max 20), 102,210 implied port calls,
from which `FactPortCall` samples the contracted 96,000.

## Alternatives considered

**Lower the contracted `FactPortCall` row count to ~31,000.** Rejected: it would
have preserved an unrealistic dimension in order to protect a number, and the
downstream KPI degradation would have remained.

**Synthesise extra calls not present in the rotation.** Rejected: a port call at
a port the vessel's own rotation does not list is a referential lie. It would
also have taught the learner to accept facts that contradict their dimensions,
which is the opposite of the point.

**Regenerate `DimVoyage` from scratch inside `dims.py`.** Rejected for now. The
dimension is otherwise correct and already validated, and a targeted, scripted,
documented revision is both smaller in blast radius and more faithful to how
this change would actually be made against a warehouse in service.

## Consequences

- `revise_voyage_rotations.py` must run after `build_dims.py` and before
  `build_facts.py`. `build_facts.py` asserts the mean rotation length and fails
  loudly if the revision has not been applied.
- Rotations touching a congestion port moved from 44% to 48% of voyages, which
  keeps the §3.3 blast radius essentially unchanged.
- `DimVoyage` is no longer byte-identical to the output of `build_dims.py` alone.
  Reproducibility is preserved because the revision is itself seeded and
  deterministic, but the two steps must be run as a pair.
- The dimension's row count, keys, and every other column are untouched, so no
  other fact or measure is affected.
