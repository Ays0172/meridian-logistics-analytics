Meridian Logistics Analytics · Day Zero

Start here

Everything you need to do before Monday, assuming no prior setup and no assumed knowledge. Roughly two hours, most of it waiting for installers.

00What you actually have

Before the steps, the picture — because it is much easier to follow instructions when you know what they are building towards.

You are building a portfolio project that stands in for real work experience. It has three parts:

  1. A fake but realistic logistics company called Meridian Global Logistics. It ships containers by sea, moves them by truck and rail, runs warehouses, and flies air freight. None of it is real, but all of it behaves like the real thing.
  2. 7.5 million rows of its operating data, generated by a Python program on your machine. Because a program makes it, you can regenerate it, make it bigger, or change how it behaves — and you can explain exactly why every number looks the way it does. That is a much stronger interview position than "I downloaded a spreadsheet".
  3. A six-week course that teaches you to model that data properly in Power BI and build five dashboards from it.

The reason this works is that the data is not random. It has a Lunar New Year slump, a peak season, a nine-week port congestion crisis in 2025, and a night shift that makes more picking errors than the day shift. Those things are hidden in the numbers, and finding them is the training.

03Generate the data

This is the step that turns an empty folder into 7.5 million rows spanning five years. It takes about three minutes of computer time.

The short version. From the project root, run .\SETUP.ps1 and walk away. It makes the virtual environment, installs the libraries, and runs every step below in order, stopping if any of them fails. That is all you need.

The rest of this section is what SETUP.ps1 actually does, because you should know what it did before you trust its output. Read it; you do not have to type it.

Still in PowerShell, from the same folder:

cd 01_generator
pip install -r requirements.txt
python build_dims.py --scale prod
python revise_voyage_rotations.py
python build_facts.py --scale prod
python validate.py
python audit.py
python crosscheck.py
python live_feed.py

What each line does, in order:

  • pip install — fetches the four Python libraries the generator needs.
  • build_dims.py — creates the 19 dimension tables: the lists of ports, customers, vessels, containers, and so on. About 20 seconds.
  • revise_voyage_rotations.py — lengthens each shipping service's port rotation to a realistic 10–20 calls. Must run before the next step; there is a written explanation of why in 00_docs/ADR.
  • build_facts.py — creates the 11 fact tables: the actual bookings, shipments, container movements, invoices, truck trips and warehouse tasks. About 100 seconds.
  • validate.py — checks the result against the 14 quality rules the schema contract sets.
  • audit.py — a second, adversarial pass that checks 67 things the contract does not state: unique keys, dates that can't run backwards, arithmetic that has to balance. Written to try to break the data rather than confirm it.
  • crosscheck.py — a third pass on what the other two both miss: relationships between tables (does a demurrage charge tie back to a container that actually overstayed?), statistical fingerprints of synthetic generation, whether every dimension member is really used, and whether the live feed's rows are distributionally continuous with the history they extend.
  • live_feed.py — brings the data up to today and, from then on, adds one new day each time it runs.

How you know it worked

validate.py should finish with 14/14 gates passed, and both audit.py and crosscheck.py with 0 errors. If it does, your data is correct: every key resolves, every container number has a valid ISO 6346 check digit, invoices reconcile to shipment revenue, and the congestion crisis is present at the right magnitude. If any gate fails, send me the output and I will fix it — do not start Week 1 on data that fails validation.

Dimension and fact — the only jargon you need today

A fact table records things that happened: a booking was placed, a container was loaded, an invoice line was raised. It is long and thin, mostly numbers and ID codes, and it grows forever.

A dimension table describes the things involved: which port, which customer, which type of container. It is short and wide, mostly text, and it barely grows.

Nearly everything in Week 1 comes back to keeping those two straight. You do not need to understand it deeply yet — Day 3 spends three hours on it.

07Keeping it live

The five years of history are frozen. Everything from today onwards arrives one day at a time, and the history can never be altered by it.

Run this whenever you like — once a day, or once a week:

python live_feed.py

It works out which days are missing and appends only those. Run it twice in one day and the second run does nothing. Leave it a fortnight and it fills the fortnight in, one day at a time.

Why it cannot corrupt what you already have

  • Append-only. New rows go into new files named for the date they carry, like part-20260827-00.parquet. The code has no path that opens an existing file.
  • Date-seeded. Each day's rows come from a seed derived from that date. So 27 August always produces the same rows, whether you generate it on the day or backfill it a month later.
  • Reproducible from the seed alone. The whole build was run twice, in separate processes, and all 689 data files came out byte-for-byte identical. That is why this package ships the generator rather than 515 MB of data files: running it gives you the dataset that was verified, not a lookalike. It was not always true — see 00_docs/ADR/ADR-002-build-determinism.md for the bug that broke it and how it was found.
  • Individually reversible. python live_feed.py --redo 2026-08-27 removes exactly that one day. Its neighbours are untouched, and regenerating it gives byte-identical rows back.
  • Self-checking. After each day it re-reads the tables and refuses to continue if it finds a duplicate key. You get told on the run that caused it, not three weeks later in a dashboard.

Want a lot of data quickly?

Don't wait for the calendar. Drive it forward directly:

python live_feed.py --until 2026-12-31

That's about four months of daily data in roughly four minutes, and it is identical to what you'd have got by waiting four months.

Making it automatic

Windows Task Scheduler is the simplest route and costs nothing — create a one-line .bat that calls live_feed.py, then schedule it daily. Because the script works out what's missing rather than assuming it ran yesterday, it doesn't matter if your machine was asleep.

The GitHub Actions route, which also gives you a real HTTPS endpoint Power BI can read, is Week 5. 00_docs/LIVE_FEED.md has both setups written out, plus the licensing traps worth avoiding.

Useful commands

live_feed.py --status   what's been appended so far
live_feed.py --until DATE  fast-forward to a date
live_feed.py --redo DATE   undo one day
live_feed.py --reset       remove all appended days, keep history

08When something breaks

'pip' is not recognizedSame cause. Or use python -m pip install -r requirements.txt instead.

MemoryError during build_factsClose Chrome and Power BI, then use --scale dev instead of --scale prod. That gives 1M rows, which is fine for Weeks 1–2.

Fewer than 14 gates passSend me the validate.py output. Don't work around it.

Rerunning from scratch

The generator is seeded, which means it produces identical data every time. So deleting 02_data and rerunning the four commands is always safe, and always gives you the same numbers back. Nothing you do to the data is irreversible.
